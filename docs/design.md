# 设计说明：从题目到实现的因果链

> 组织方式：**问题 → 动机 → 设计 → 选择 → 演进 → 开放**。每一层都由"为什么这么选、而不那么选"驱动。文末是开放问题而非定稿——这套设计预期随评测结果继续演进。

## 0. 一句话

把这道"知识库 + Agent 检索"题，当作一个**评测驱动的 RAG 工程问题**来做：先有可跑的质量指标，再让架构、消融、迭代决策都挂在这根指标上。

## 1. 问题（Problem）

题目表面是 5 个功能点：知识库 CRUD+分页、上传(txt/文本)、相关性/语义检索、流式返回、封装成 agent 可调用的 MCP tool。

但拆开看，真正的难点只有一个，且藏在第 3 点里：**检索质量没有标准答案。** "春天"要搜到《春》、"小孩子"要在毫无字面重合的情况下搜到《故乡》——对不对，无法靠读代码判断，只能在一组样例上度量。

而题目把这组样例白送了：

| query | 期望命中 | 字面重合 |
|---|---|---|
| 春天 | 《春》 | 高（"春"⊂"春天"）|
| 少年闰土 | 《故乡》 | 高（实体，原文出现）|
| 小孩子 | 《故乡》 | 零（纯语义改写）|

**为什么不直接当成 5 个 CRUD/检索功能写完？** 因为那样"小孩子→故乡"是否真的工作全凭手感；任何"换模型 / 调 chunk / 加 rerank"的改动都无法判断变好还是变坏，合并全靠感觉。

## 2. 动机（Motivation）

由问题推出唯一的动机：**先把这 3 条样例变成可跑的评测（Recall@k / MRR），再写功能。**

有了客观指标，后面想做的工程动作才有支点：

- 消融 = 关掉一个组件看指标掉多少；
- A/B = 两套配置同评测集比分；
- PR 合并门槛 = 必须带指标 delta。

**为什么先评测、不先功能？** 先功能意味着优化没有锚点——等于把背过的 trick 随机往系统上套，是"随机试药"。先评测，把"试药"变成"对照实验"。

## 3. 设计（Design）

设计的任务，是让上面的动机在物理上可行。三条原则：

### 3.1 核心是纯库，REST 和 MCP 都是薄适配器

- **为什么**：一份检索实现，两个入口（Web 知识库走 REST，agent 走 MCP）；更关键的是评测可以**直接打核心库**，不经过 HTTP/MCP。
- **为什么不**把检索逻辑写进 MCP handler：那样评测要穿过协议层、无法复用、无法单测，动机直接落空。

### 3.2 检索每个环节是一个可替换策略（Strategy）

Chunker / Embedder / Retriever / Reranker / QueryTransform 各自一个接口。

- **为什么**：消融的物理前提就是"可替换"——不可换的组件没法消融。每个实验 = 选哪几个策略组装一条管线 = 一个配置文件（配置即组装）。
- **为什么不**先写死一条"最优"管线：因为"最优"是评测跑出来的结论，不是先验假设。写死 = 放弃了用数据证明的机会。

### 3.3 检索是单次原语，多跳留给调用方 agent

- **为什么**：题目的 agent 集成是单次 tool call。agent 想多查，可以自己多次调用这个原语——编排层本就属于 agent。
- **为什么不**自己做多跳 / 规划：那是重复造 agent 已有的能力，且为题目没要求的形态做防御 = 过度工程。MCP tool 因此只返回结构化的「chunk + 来源 + score + snippet」，让 agent 的上下文（它的工作记忆）保持干净，而不是把整篇灌回去。

## 4. 选择（Choices）

骨架定了，下面是三个真正有权衡的岔路口，每个都写清"为什么走这条、不走那条"。

### 选择一：仍做向量检索，而非纯长上下文全塞

- **岔路**：语料初始只有 2 篇短文，全文塞进 context 物理上完全放得下。诚实地说，纯长上下文对 n=2 是成立的。
- **选向量检索**：① 题目显式要求向量检索能力，这是考察点；② 架构不能假设"语料永远塞得下"，要面向 N 增长；③ 把全塞保留为**评测上界(oracle)**——检索若追不平它就是在丢信息，比嘴上说"RAG 更好"可验证。
- **不选纯长上下文**：扩展性差，且回避了题目考点。
- **不选 agentic 多跳**：超出 scope（见 3.3）。
- **代价**：n=2 时检索相对全塞没有明显收益。所以必须把评测做难——chunk 级检索 + 加几篇风格相近的干扰文档，否则消融全是 0 delta。

### 选择二：hybrid 检索（BM25 + dense），而非单一通路

- **岔路**由 golden set 直接逼出：三条 query 跨越两个相反的轴。"小孩子"零字面重合，**只有 dense 能召回**，BM25 全灭；"少年闰土""春天"是精确词 / 实体，**sparse 更稳**。
- **不选纯 dense**：丢掉精确词命中的稳健性。
- **不选纯 BM25**："小孩子"直接挂掉。
- **选 hybrid**：两轴互补。但**不是一上来全开**（见演进）。
- **为什么不一把全开** hybrid+rerank+rewrite：无法归因每个组件各贡献多少，且是典型过度工程。

### 选择三：本地中文 embedding，而非 API

- **选本地**：离线可复现、免费、中文强，且模型本身就是一根消融轴（small ↔ base ↔ large ↔ m3e）。
- **不选 API**：引入 key / 网络 / 成本依赖，损害 demo 可复现性。
- **不一上来用最大模型**：先 small 起步，让评测决定是否值得为更大模型付代价。

### 选择四：评测判分用文档级；margin 只作同配置族内的脆弱性信号

- **岔路**：要让评测有判别力，直觉是标注"哪个 chunk 才算对"（chunk 级 gold）。
- **不选 chunk 级**：哪一段算对没有客观标准，且需大量人工——成本高、主观、不可持续。
- **选文档级**：判分只问"top 结果是否来自 gold_doc"（客观，题目已给：小孩子→故乡）。
- **margin 的位置**：margin＝最佳 gold 分 − 最佳非 gold 分，用来发现"Recall 已满但排序很脆"的情况；它只在同模型、同语料、同 chunker 等控制变量一致时可横向比较。
- **不把 margin 当全局目标**：不同 embedding 模型的 cosine 分数尺度未必可比，所以不能用一个模型的 margin 门槛去验收另一个模型。margin 指向风险，不替代 Recall/MRR 与更覆盖的语义评测集。

### 选择五：query 侧变换默认不做；要做必须"路由 + 接地 + 评测门控"

- **背景**：exp-002 给 query 加统一指令前缀，q3 反从 rank1 掉到 rank3——一次无条件、无业务接地的 query 变换，把 query 推离了文档语言，margin 下降正是这件事的度量。
- **决策**：query 侧改写 / 前缀 / 扩展默认**不启用**。若将来要用，必须同时满足：① **路由**（只对需要的 query 改，简单或已命中的不动）；② **接地**（往语料 / 业务语言靠，而非通用语言）；③ **评测门控**（margin/recall 对照证明有益才留）；④ **禁止对 gold query 手调**（= 数据泄漏）。
- **不选** 无条件改写 / HyDE / LLM 改写：要么把 query 拉离文档语言，要么把 LLM 引入本应 LLM-free、确定性的检索与评测路径。
- **本轮影响**：exp-002 作为负结果留档；不再把通用前缀当作默认增强路径。

### 选择六：先扩语义评测集，再加增强层

- **背景**：exp-001 在 3 条 golden query 上已经 Recall@1=1.0，但 q3 margin 很小；这说明"有脆弱信号"，不等于"必须立刻换模型或加组件"。
- **不直接换大模型**：只有一条语义 query 时，换 embedding 很容易变成围绕单题调参；且跨模型 margin 不可直接比较，无法支撑"明显更好"的验收。
- **选先扩 semantic stress set**：先增加自然的零字面重合查询（例如小孩/儿童/孩童/儿时伙伴/童年伙伴/少年形象/农村少年），只改评测集、不改检索。若 dense-only 仍稳，则停止；若失败，再根据失败形态选最小杠杆。
- **增强层排序**：文档增强 / rerank / query expansion / 更大 embedding 都是菜单，不是计划；只有 stress set 暴露具体失败后才打开对应项。
- **本轮结果**：审计后的 semantic stress set 显示 dense-only 排序不稳；cross-encoder rerank top10 是当前 P2 默认候选。query instruction 继续回滚，文档增强 / query expansion / 更大 embedding 不启用。

## 5. 演进（Evolution）

怎么从骨架长成成品——一条"假设 → 实验 → 决策"的链，而不是各模块憋大招。

1. **v0.1 走骨架**：dense-only + 固定 chunk，端到端打通（入库 → 检索 → MCP 可调用 → 评测跑绿）。
   - 为什么骨架先于优化：先保证端到端可跑，避免在局部最优上反复堆叠。
2. **诊断驱动拉杆**：跑 golden set，看哪条 fail，沿一条从上游到下游的定位链——答案在不在库 → chunk 切碎没 → query 和文档有没有语义鸿沟 → embedding 适不适配 → 是不是召回了但排在 TopK 外。**只拉定位到的那一段杠杆**，重跑，记一行 leaderboard + 一句决策。
   - 为什么只拉一个杠杆：可归因（知道是哪个改动起的作用）+ 防过度工程。
3. **评测覆盖优先**：若 golden set 已全绿但暴露脆弱信号，先补同类评测样例，而不是马上堆组件。
   - 为什么先扩评测：否则优化会围着单题 margin 打转，结论不可泛化。
4. **停止规则**：扩展后的 golden set 全绿即停，不再为"还能更好"继续堆组件。
   - 这条停止规则，就是把"不为没出现的问题过度设计"落进流程。
5. 每一步 = 一个 PR + 一行 leaderboard + 一句决策 → git 历史本身成为决策叙事。

消融矩阵（见 `experiments/README.md`）是这条链的"菜单"，不是计划：诊断决定点哪几道，没被指向的不跑、不写文档。

## 6. 开放（Open）

刻意留白的部分，以及"什么信号出现才重新打开它"——在那之前不为它设计。

| 开放项 | 现在不做的原因 | 复审触发 |
|---|---|---|
| 查询路由（一次检索够 vs 多跳）| 题目是单次 tool call，模型自判易把简单问题复杂化 | 出现明确多跳问题形态 |
| 在线 A/B | 需要真实流量；离线 A/B 已能给出严谨结论 | 有线上流量后 |
| 失败分布自动监控 | 上线后才有分布可言 | 系统上线 |
